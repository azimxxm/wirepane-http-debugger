## Goal and roadmap

@README.md

The README (in Uzbek) is the source of truth for the goal, setup and roadmap: **Wirepane**, a free HTTP debugger for developers, QA and beginners, a Proxyman alternative built on HTTP Toolkit's open-source code and shipped as one app for macOS, Windows and Linux (GitHub `azimxxm/wirepane-http-debugger`, bundle ID `com.wirepane.app`). Its own version is the root `VERSION` file (`1.0.0`). Update it when the plan changes. Markdown files are tracked in this repo (docs will be written as `.md`), which overrides the global "only README.md is tracked" rule.

## Branding

User-visible text says "Wirepane". That includes the CA: the server creates its own "Wirepane CA" in `wirepane-ca.pem` / `wirepane-ca.key` (`generateHTTPSConfig` in `httptoolkit-server/src/index.ts`). The official app's `ca.pem` / `ca.key` share the same config folder and are never touched. Phones download the certificate from `http://wirepane.cert/certificate`; `wirepane.cert` is not a real domain, the proxy answers it through the built-in rules in `httptoolkit-ui/src/model/rules/rule-creation.ts`. `amiusing.httptoolkit.tech` still works the same way.

These keep the "HTTP Toolkit" name on purpose, don't rename them:

- The `HTTP Toolkit Rules` title in saved rule files (file format), the HTTP Toolkit Android app (its real Play Store name) and links to httptoolkit.com docs.
- Internal identifiers: package names, the server's `httptoolkit` config dir (env-paths, with the CA), `HTK_*` / `HTTPTOOLKIT_*` env vars, `amiusing.httptoolkit.tech`.
- The internal app and server version, `1.27.2` (`version` in the desktop and server `package.json`): the UI checks it to turn features on. Wirepane's own version is the root `VERSION` file, used for file names, the release tag, the macOS About panel ("1.0.0 (based on HTTP Toolkit 1.27.2)", `src/product-version.ts`) and Settings > Status (`WIREPANE_VERSION` at UI build time). So Finder, Windows' app list and `apt` still show 1.27.2.
- "HTTP Toolkit Pro" texts still inside upstream components: those prompts never render any more (see Architecture), so they stay untouched to keep syncs small.

The packaged app's Electron identity is Wirepane (`extraMetadata` in `httptoolkit-desktop/package.json`: name `wirepane`, productName `Wirepane`), so it shares nothing with the official app: userData, electron-store and the single-instance lock are in `~/Library/Application Support/Wirepane` (`%APPDATA%\Wirepane`, `~/.config/Wirepane`), logs in `~/Library/Logs/Wirepane`. The About/Hide/Quit menu items say Wirepane (`src/menu.ts`). Dev runs use the same folder too (the dev Electron's productName is Wirepane, and APFS ignores case), so the installed app and `./start.sh` can't run at the same time: the second one quits straight away. That's accepted. The CLI/MCP socket is ours as well: `wirepane-ctl.sock` / `\\.\pipe\wirepane-ctl` (`CTL_SOCKET_NAME` / `CTL_PIPE_PATH` in `httptoolkit-server/src/api/ui-operation-bridge.ts`, which `bridge-client.ts` shares), because the server removes an existing socket before it listens. On Linux the executable is `wirepane` (`/opt/Wirepane/wirepane`, `/usr/bin/wirepane`) and the packages are named `wirepane`, clear of the official app's `httptoolkit`.

The logo source is `brand/icon.svg`, and `brand/tray-template.svg` is its one-colour menu bar version. `./brand/build-icons.sh` regenerates every icon and logo file from it (`httptoolkit-desktop/src/icons/*`, `httptoolkit-ui/src/images/logo-icon.svg` and `loading-logo.png`), so change the source and rerun the script instead of editing those files.

## Distribution: unsigned, on every OS (no Apple Developer account yet)

There is no Apple Developer account and no code signing certificate, so nothing may depend on one. The owner is applying for the Apple one; until it arrives:

- Every installer is unsigned and the build works on a machine with no certificates: no `notarize: true`, `forceCodeSigning`, `CSC_*` / `WIN_CSC_*` identities, Azure signing, provisioning profiles or App Store steps in the default build.
  - **macOS:** an unsigned `.pkg` for Apple Silicon (`arm64`) holding an ad-hoc signed `Wirepane.app` (`codesign --sign -`, which Apple Silicon needs to run it at all), plus the same app as a `.zip`. Gatekeeper blocks a downloaded unsigned `.pkg` on the first open: right-click → Open, or System Settings → Privacy & Security → **Open Anyway**. A `curl … | sh` install avoids the quarantine flag.
  - **Windows (x64):** an NSIS installer (`-setup.exe`, per-user, the folder can be changed) and a `.zip`. SmartScreen warns: **More info** → **Run anyway**.
  - **Linux (x64):** `.AppImage`, `.deb` and `.rpm`. The AppImage needs `chmod +x` (and `--no-sandbox` where Ubuntu 24.04+ blocks Electron's sandbox; the `.deb` installs an AppArmor profile instead).
  - The README and the release notes (`.github/release-notes.md`) say all of this.
- Build the installers only when the owner says "done, publish", and the release workflow is started by the owner.
- Releases ship only the macOS arm64 `.pkg` for now (v1.0.0, 2026-10-12). Windows and Linux stay "coming soon" in the README and the release notes until the owner says to release them, although the scripts and the workflow already build them. Until then, release-only fixes go on the publish checklist in `docs/remaining-work.md` section 7, not into code.
- When the Apple account arrives, signing and notarization are added on top: a Developer ID Application/Installer identity, hardened runtime, notarization. The unsigned path stays as a fallback.
- How it's built: `./scripts/build-release.sh <mac|win|linux>` on that OS (Commands), and `.github/workflows/release.yml` on GitHub. `npm run build` in `httptoolkit-desktop` uses `build-setup/wirepane-builder.config.cjs`: file names with the `VERSION` (`Wirepane-<version>-mac-arm64.pkg`, `-win-x64-setup.exe`, `-linux-amd64.deb`…); mac `pkg` and `zip` for arm64 with `identity: '-'` (ad-hoc), `hardenedRuntime: false` (with an ad-hoc signature its library validation stops the app from starting) and an unsigned pkg; Windows `nsis` and `zip` for x64 with upstream's Azure signing removed; Linux `AppImage`, `deb`, `rpm` for x64 with our executable name, maintainer (`Wirepane <azimxxm@users.noreply.github.com>`) and `build-setup/wirepane-rpm-after-remove.sh`; any `CSC_*` variables dropped. `ENABLE_SIGNING=true` switches to upstream's signed setup (`electron-builder.config.cjs` and `build` in `package.json`), which is where the Developer ID identity and notarization go later.

## Repo layout

Three upstream HTTP Toolkit projects, imported with `git subtree --squash` (no upstream history):

- `httptoolkit-server/`: Node + TypeScript oclif CLI. Runs the proxy, the interceptors and the API the UI calls.
- `httptoolkit-ui/`: React + MobX app bundled with webpack.
- `httptoolkit-desktop/`: Electron shell that starts the server and loads the UI.
- The proxy engine `mockttp` is an npm dependency, not part of this repo.
- `bruno/`: Bruno (MIT, usebruno/bruno), tracked for its packages: `bruno-converters` (Postman/Insomnia/OpenAPI import), `bruno-lang` (`.bru` files), `bruno-js` (scripts/tests runtime), `bruno-cli`. It is not run as an app. Its UI is Redux-based, so Wirepane screens are written in our own React + MobX stack and use Bruno's packages for the logic. Keep its `license.md` notices.
  - The server runs our copy, not the npm releases: `httptoolkit-server/package.json` links `bruno-common`, `bruno-lang`, `bruno-schema`, `bruno-converters` and `bruno-filestore` with `file:../bruno/packages/...`, and those packages load their own dependencies from `bruno/node_modules`.
  - We change Bruno's code on purpose; it doesn't have to match upstream. Fix Bruno bugs there instead of working around them in the server. Mark every edit with a `// wirepane:` comment and keep the diff small, so syncs show our edits clearly. Update Bruno's own tests along with it: `npm run test:ci --workspace=packages/bruno-converters` inside `bruno/`.
  - `scripts/build-bruno.sh` installs what those packages need (`npm ci` with `--workspace` flags, from Bruno's own lockfile) and builds `bruno-common`, `bruno-schema-types`, `bruno-converters` and `bruno-filestore` into `dist/`. `./setup.sh` runs it. It must run again after every Bruno sync, or the server keeps the old build. Re-runs skip what is up to date; `--force` redoes everything.

`./sync-upstream.sh` runs `git subtree pull --squash` for each folder, Bruno included (needs a clean tree). Every line we change in upstream files can conflict on the next sync, so keep fork changes small and contained, and prefer adding new files over rewriting upstream ones.

## Commands

From the repo root (macOS, Node 24):

- `./setup.sh`: builds Bruno's packages (`scripts/build-bruno.sh`), then `npm ci` in all three projects. Re-run whenever a `package-lock.json` changes, e.g. after a sync.
- `./start.sh`: runs the whole app from local source, logs go to `logs/`. Server (`npm start`, restarts on change) on :45457 (API) and :45456 (Mockttp admin); UI (`npm run start:web`, webpack-dev-server with hot reload) on :45458, set in `automation/webpack.dev.ts` and clear of the usual dev server ports; then it compiles the desktop TypeScript and opens Electron with `HTK_DEV=true APP_URL=http://localhost:45458`. Cmd+Q or Ctrl+C stops everything. Extra args go to Electron, e.g. `./start.sh --remote-debugging-port=9222`.
- `./scripts/build-release.sh <mac|win|linux>`: builds that OS's installers from this repo, on that OS (macOS on Apple Silicon, Windows x64 in Git Bash, Linux x64 with `rpmbuild`), and lists them: `httptoolkit-desktop/dist/Wirepane-<VERSION>-mac-arm64.pkg` and `.zip`; `-win-x64-setup.exe` and `-win-x64.zip`; `-linux-x86_64.AppImage`, `-linux-amd64.deb`, `-linux-x86_64.rpm` (plus the unpacked app, e.g. `dist/mac-arm64/Wirepane.app`). `./scripts/build-pkg.sh` is the mac shortcut. In order:
  - `scripts/build-bruno.sh`;
  - `scripts/build-server.sh <target>` (`darwin-arm64`, `win32-x64`, `linux-x64`; this machine's by default): tsc, oclif manifest and the rspack bundle with Bruno inside; Node.js 24.19.0 for the target from nodejs.org, checked against SHASUMS256 and cached in `build/cache`; the release's `node_modules` (only `oclif.dependenciesToPackage`) installed by `npm ci` in `build/server-deps/<target>` with that Node.js's own npm, from a lockfile cut out of the server's (`scripts/stage-server-deps.cjs`), then `npm rebuild` for the target's prebuilt native binaries; `scripts/assemble-server.cjs` writes `build/server/<target>/httptoolkit-server` (launcher, `bin/node[.exe]`, `nss/<os>`) and checks every native binary's OS and CPU. On this machine's own target it then starts the release, which has to answer only `wirepane://app`, load `tls-impersonate`, read a `.bru` collection and import a Postman one. Another target is only assembled: `./scripts/build-server.sh win32-x64` works on a Mac as a dry check;
  - the UI (`DISABLE_UPDATES=true npm run build`, no Sentry/PostHog keys), then `scripts/assemble-ui.cjs` copies it to `build/ui` with the ~2500 API specs brotli-compressed (387 MB → 28 MB);
  - the desktop (`npm run build`, with `WIREPANE_SERVER_TARGET`).
  Takes a few minutes on a Mac; every run rebuilds from the current code. Build outputs stay in the gitignored `build/` and `httptoolkit-desktop/dist/`.
- `.github/workflows/release.yml`: the release on GitHub. Actions → Release → Run workflow (input `version`, empty = `VERSION`), or a pushed `v*` tag (has to match `VERSION`). One job per OS (`macos-14`, `windows-2022`, `ubuntu-22.04`, Node 24.19.0) runs `./setup.sh` and `./scripts/build-release.sh`, then a last job puts the 7 files and `SHA256SUMS.txt` in a **draft** release `v<version>` with `.github/release-notes.md` (`gh release create --draft`, `GITHUB_TOKEN` only). Actions are pinned to commit SHAs. Lint it with `npx --yes @tktco/node-actionlint .github/workflows/release.yml` and `npx --yes @action-validator/cli .github/workflows/release.yml`.
- `WIREPANE_HIDDEN_WINDOW=1 <Wirepane.app>/Contents/MacOS/Wirepane --remote-debugging-port=9333 --use-mock-keychain`: runs a built app with nothing on screen (no Dock or menu bar icon, no dialogs, window never shown) for checks over CDP. Point `HOME`, `CFFIXED_USER_HOME` (Electron's userData) and `TMPDIR` at a throwaway folder with a short path (the server's CLI socket, `wirepane-ctl.sock`, goes in `TMPDIR` and must fit 104 characters), so the check touches none of your data, and its single-instance lock doesn't clash with an installed Wirepane that's running. `kill -TERM <its pid>` quits it like Cmd+Q, server included.

Inside each project folder:

|                    | `httptoolkit-server`                                    | `httptoolkit-ui`                                                                                    | `httptoolkit-desktop`                              |
| ------------------ | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| Type-check / build | `npm run build:src` (tsc → `lib/`)                      | type errors show in `logs/ui.log` (ForkTsChecker); `npm run build` makes the prod bundle in `dist/` | `npm run build:src` (tsc → `build/`)               |

No project has a lint script.

Pitfalls:

- `server:setup` downloads the official server release from GitHub instead of using `../httptoolkit-server`. It runs inside UI `npm start` / `test:integration` and desktop `npm start` / `npm test`, never in the desktop's `npm run build`, which packages `build/server/<target>` from `scripts/build-server.sh`. Use `./start.sh` for local runs.
- UI integration tests also need puppeteer's Chromium, which `setup.sh` skips on purpose (puppeteer 5 has no Apple Silicon build).
- The server rejects requests whose `Origin` isn't in `ALLOWED_ORIGINS` (`httptoolkit-server/src/constants.ts`): any localhost / 127.0.0.x origin in dev, only `wirepane://app` (the bundled UI) in prod builds (`HTTPTOOLKIT_SERVER_BINPATH` set, which our release launcher always does). Even health checks need it: `curl -H "Origin: http://localhost:45458" http://127.0.0.1:45457/version`.
- Server `engines` pins Node `v24.19.0`; other 24.x versions work with an `EBADENGINE` warning. npm skips the optional `tls-impersonate` (TLS fingerprint mirroring) below 24.19, which is why the release installs its `node_modules` with its own downloaded Node.js.
- The release runs the server's rspack bundle, dev runs its unbundled source with Node's own `require`, so a bundling mistake only shows in releases. For node targets rspack prefers a package's `module` (ESM) entry, and an ESM build can export something different from the CommonJS one Node loads: bundled ohm-js had no `grammar`, so no `.bru` file could be read ("n.grammar is not a function", then "Cannot access 'e_' before initialization"). `rspack.config.js` therefore resolves everything under `../bruno` like Node (`mainFields: ['main', 'module']`), and `scripts/build-server.sh` reads a collection with the built release. Test changes to Bruno's packages or the bundle config with a release build, not only `./start.sh`.
- The release scripts run in macOS's bash 3.2 and in Git Bash on Windows: no `mapfile` or other bash 4 features, no empty arrays under `set -u`, paths passed as arguments rather than in env vars. The workflow sets `core.autocrlf false` on Windows, because CRLF scripts don't run in bash.
- In the UI, plain `npx tsc --noEmit` fails on DOM vs WebWorker lib conflicts inside `node_modules`. The dev server's ForkTsChecker is the real type check: look for `No issues found.` in `logs/ui.log`.
- Everything runs natively on Apple Silicon without Rosetta. The only x86_64 binary in `node_modules` is node-notifier's `terminal-notifier`, and `httptoolkit-ui/automation/webpack.common.ts` skips it there, because its failed spawn used to kill the UI dev server.
- The global auto-lint hook runs `prettier --write` on every file changed with Edit/Write. `.prettierignore` keeps it off the upstream folders, but only when the hook runs from the repo root. After editing upstream code, check `git diff --stat` for whole-file reformatting, or make those edits with sed/python.

## Architecture

1. Electron (`httptoolkit-desktop/src/index.ts`) creates a random auth token, spawns `httptoolkit-server start` with it (`HTK_SERVER_TOKEN`) and loads `APP_URL` with the token in the query string. The default is the UI bundled in the app: `src/bundled-ui.ts` serves `Resources/httptoolkit-ui` from the privileged scheme `wirepane://app` (fixed origin, so localStorage/IndexedDB survive restarts; client-side routes fall back to `index.html`). The packaged server is ours from `Resources/httptoolkit-server`, started by our own launcher (`bin/httptoolkit-server`, or `bin\httptoolkit-server.cmd` on Windows, written by `scripts/assemble-server.cjs`), which never switches to a server downloaded into `~/.local/share` or `%LOCALAPPDATA%`. The UI's API specs ship as `api/**/*.json.br`; `bundled-ui.ts` streams them out decompressed (`createBrotliDecompress`) under their `.json` name and type. `src/preload.cts` exposes `window.desktopApi`, which the UI reads in `src/services/desktop-api.ts`. With `HTK_DEV=true` it uses fixed ports 45457/45456 and spawns a stub (`build-setup/skip-server.ts`) instead of the server; `start.sh` runs the real server separately, without a token.
2. The server (`httptoolkit-server/src/index.ts`) starts two listeners. The Mockttp admin server (:45456) is what the UI uses directly to create and drive proxy sessions (`PluggableAdmin.AdminClient` in `httptoolkit-ui/src/model/proxy-store.ts`). The HTK API (:45457, `src/api/`: REST in `rest-api.ts`, GraphQL in `graphql-api.ts`, shared logic in `api-model.ts`) covers what a browser can't do: certificates, interceptors, system state.
3. Interceptors (`httptoolkit-server/src/interceptors/`: browsers, Android via ADB/QR, Docker, Electron apps, Frida, JVM, terminal) launch or reconfigure a target so its traffic goes through the proxy.
4. Config and the CA live in `env-paths('httptoolkit')` (`~/Library/Preferences/httptoolkit` on macOS), shared with the official app. Renaming that directory forces everyone to reinstall the CA on their devices, so a rebrand should change user-visible names only and leave internal ones alone. The exception is oclif's own folders: the server's `oclif.dirname` is `wirepane-server` (`~/.local/share/wirepane-server`, `~/Library/Caches/wirepane-server`), because `~/.local/share/httptoolkit-server/client` holds the official app's downloaded servers. The server has no `@oclif/plugin-update` any more: its init hook ran `update --autoupdate` every 14 days and would fetch the official server from GitHub.
5. The `ctl` and `mcp` server commands (`src/commands/`) expose the UI's operations to CLIs and MCP clients through `src/api/ui-operation-bridge.ts`; the desktop app ships `httptoolkit-ctl` / `httptoolkit-mcp` wrappers for them.

UI state lives in MobX stores under `httptoolkit-ui/src/model/` (proxy session, captured events, rules, interception, send, account). Everything is free. `AccountStore` (`model/account/account-store.ts`) is one fixed full-access user with no account servers, so every upstream paid check (`user.isPaidUser()`, `mightBePaidUser`, `NonPaidStepClasses` in `model/rules/rules.ts`) passes, and the server's `src/api/ui-operation-bridge.ts` gives every CLI/MCP caller full access. Login, plan picker, checkout and the settings account card are deleted; keep them out when syncing upstream. Heavy work (body decoding, formatting, OpenAPI building, cert parsing, zip export) runs in a web worker, `src/services/ui-worker.ts`. Messages and yes/no questions use our own themed dialogs, `messageDialog()` / `confirmDialog()` from `src/model/ui/dialogs.ts` (shown by `components/common/dialog-host.tsx`), never `alert()` or `confirm()`.
